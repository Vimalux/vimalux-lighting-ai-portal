# Partner role safe release (staging only)

Base main: `96b6d540e754a83f0a7e6b5bb49ab851beda2898`.
Inspected staging parent: `9abb9ec268e15d057eaf60bd3288b752efffbd9c`.
No production deployment or merge is part of this change.

## Reproduced regression

The unmodified staging source passed 316 of 318 tests. It failed both the
VIMALUX partner economics test and the dashboard Adaptive Dimming label test.
The committed App differed from the code generated by the patch workflows.

The default LCU has brand VIMALUX. The new catalogue-derived CMS partner set
therefore contained VIMALUX. `partnerProjectRows` selected all VIMALUX projects,
but then incorrectly entered the CMS-only allocation branch. It returned 500
of CMS ARR instead of 500 + (20 × 6) = 620 including annual additional service.
It also returned only 5,474.860499868929 of CMS contract services instead of
the full 30,788.82701983747 contract revenue (24,000 CAPEX + 6,788.827019837471
escalated services). The consolidated VIMALUX branch now always returns the
existing calculation engine's annual recurring revenue and total contract revenue.
The original 620 expectation is unchanged.

## Model and compatibility

- `partnerRole` or `partnerRoles`: CMS, ADAPTIVE_DIMMING, HYBRID_LIGHTING, GENERAL.
- `partnerName`: service partner identity; independent of product `type` and `supplier`.
- `compatiblePartners`: optional list for explicitly compatible hardware.
- Existing `cmsPartner`, vendor/supplier/brand metadata remains a read-only fallback.
- Untagged legacy FELICITY products infer Adaptive Dimming, never CMS. Explicit
  CMS metadata permits FELICITY CMS. Other suppliers can use the same metadata.
- Untagged non-FELICITY CMS hardware retains its prior CMS classification;
  untagged Other equipment is General, not automatically Adaptive Dimming.
- No saved identifiers, `powerAid*` fields, product prices, or SKUs are migrated.
  Catalogue role/partner/compatibility controls use the existing admin catalogue path.
- CMS changes preserve compatible hardware and all Adaptive Dimming equipment.
  Adaptive changes remove only incompatible adaptive selections.
- Reports are keyed by actual partner and role used in the selected project scope.
  One partner may have two role reports. Consolidated VIMALUX is never summed
  from supplier reports. CMS retains CMS recurring sales; Adaptive Dimming retains
  the existing supplier fee share. General/Hybrid equipment reports derive supplier
  equipment costs and escalated annual costs from selected catalogue items, assigning
  each item to one role. They do not alter customer pricing or VIMALUX calculations.
- Procurement groups by actual seller. Internal previews retain costs; supplier PDFs
  contain specifications, SKU, quantity and unit only. The unused legacy CSV helper
  also omits costs; the user-facing export remains PDF.
- Virtual equipment costs are calculation-only and idempotent. Stored additional
  costs are never rewritten or duplicated.

## Validation and preserved behaviour

The five production economic regressions removed earlier on staging are restored:
CMS dependency, ROI, weighted TCV, probability normalization, and stage averages.
No economic expectation was reduced. The staging test that excludes disabled
Adaptive Dimming projects is retained: this follows the requirement to report
actual active partner usage; revenue assertions are unchanged. Only display-text
and moved-PDF-source assertions are updated to follow the requested rename/extraction.

Full result objects were compared against the original main calculation wrapper
in 12 cash/finance/LaaS × CMS × Adaptive Dimming scenarios without new equipment:
all identical. Core calculations, identity, persistence, deduplication, navigation,
and permission implementations remain unchanged. Agent deletion callback suppression
and read-only/pricing guards have regression coverage.

The built app was exercised in an isolated browser with staging catalogue records
and clearly synthetic alternative partners: selector filtering, independent partner
changes, preserved general equipment, reload/menu restoration, separate DATEK and
FELICITY reports, and downloaded supplier PDFs. No production requests or browser
exceptions occurred. Supplier and partner PDF pages were visually inspected.

## Reproducible build

All 11 obsolete source-mutation workflows and the three staging patch scripts are
removed on this branch. `staging-validation.yml` checks out the event commit with
read-only permissions, runs `npm ci`, `npm test`, `npm run build`, and rejects
tracked-source changes. Vercel uses the same committed build/install commands via
`vercel.json`. No workflow pushes another commit or patches App after checkout.

The existing isolated staging Supabase configuration is unchanged. Preview is a
local editing sandbox using the staging catalogue; it does not save production
Business Cases. Production promotion requires a separate release decision.
